## Site practice: git, worktrees and parallel sessions

classifier_blocks_rule_mandated_git: The auto-mode permission classifier refused, as "Git Destructive", a `git push --force-with-lease` after a rebase (raid 6530fd, 2026-10-28) and `git branch -D`, `git push origin --delete` and `git update-ref -d` on superseded branches the author asked to delete (2026-10-29). The blanket Bash allow does not exempt them. On 2026-10-29, with the author's permission, narrow allow rules were added to the user settings and took effect mid-session; `git update-ref -d` was still refused, tagged "Self-Modification". The same day `raid_land.py` on a ticket-only PR was refused as "Merge Without Review" until the author said "merge it". How to apply: do not retry or work around a denial; give the author a one-shot `!` command with pinned leases, and point at the narrow allow rules (force-with-lease, branch -D, push origin --delete) unless already present.

check_exit_codes_not_pipe_tails: On 2026-10-21, `git rebase origin/main 2>&1 | tail -1 && git push --force-with-lease ...` on PR 1568 pushed a half-finished rebase: the rebase stopped on a conflict, but the pipeline returned tail's status. The remote branch briefly equalled main and GitHub closed the PR; it was fixed and reopened. How to apply: for any git command whose success gates the next step, redirect output and test its own `$?` before the dependent command; never chain a force-push after a piped rebase.

sync_local_main_after_merge: In the 2026-10-27 raid (13 merges in about an hour) merges were hand-rolled and the merge recipe's sync step (`scripts/sync-local-main.sh . main`) was skipped. The primary checkout's main stayed at the morning tip, and every `$IDH_ROOT/scripts` helper, which resolves to the primary checkout, ran stale code: a helper kept failing on a bug already fixed by PR #1742. How to apply: treat the sync as part of the merge and read its result line; when a helper misbehaves after a fix merged, compare `git rev-parse main origin/main` in the primary checkout first.

vscode_sessions_share_worktree: Claude Code sessions started from one VS Code workspace all run in that workspace's worktree. On 2026-10-26 three sessions committed into one branch while a /gaze of PR 1664 ran; the review saw the head move and ended ESCALATE, and one session's uncommitted edits sat in another's tree. How to apply: at session start in VS Code, list peer sessions; if one shares the worktree, say so before any commit, push or review.
