Decided by the author on 2026-09-16, closing two proposed additions to
`rules/workflow.md` that had come out of a single session's incidents: "ce n'est
pas le moment d'agrandir le workflow". The pipeline he named is

    project memory → global memory → crystallisation into rules

and the instruction that goes with it is blunt: **stop pushing directly into the
harness.** A rule body is not the place a lesson is first written down.

**Why:** `rules/README.md` records that the resident set costs roughly 12 800
tokens in every session, of every project, forever, and
`tests/test_rules_resident_budget.py` exists because bodies grow one incident
bullet at a time. A lesson written straight into a rule has been paid for before
anyone knows whether it recurs. Routed through memory it costs one project's
index line, and it earns promotion only by showing up again somewhere else —
which is the same evidence test the `/dream` promotion gate already applies. The
harness has a recorded tendency to build second-order tooling under pressure
(`feedback_harness_cooldown_stop_second_order_tooling`); this closes the fastest
path by which that happens.

**How to apply:** when a session produces a lesson, write it as a memory in the
project where it happened, and stop there. If it proves general, it reaches
global memory. Only a lesson that has survived both stages is a candidate for a
rule body, and that promotion is the author's call, never a peer's and never an
agent's own. This is not self-contradictory for the memory you are reading: a
memory is the sanctioned first stage, and it is what this decision is recorded
as rather than as the rule edit it forbids. Two sessions refused to edit rules on
a peer's go-ahead on the same day this was decided; both were right, and this
generalises their instinct into standing policy. Related:
[[feedback_dont_codify_hard_rules]], [[feedback_harness_is_the_deliverable]].
