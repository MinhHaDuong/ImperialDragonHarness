When the user describes something with a hedge — "typically", "usually", "often", "various ways" — **keep it soft**. Do not re-state it as an absolute rule or a crisp discriminator. The user's domain knowledge is curatorial judgment with typical patterns AND exceptions, not a rule engine.

**Why:** During the 0486/reference-boundary design dialogue (2026-06-09) the user corrected this repeatedly. "Projects *typically* propose power complexes" → I wrote "the project unit IS the complex." "PDP have many developer-less wishlist projects" came after I'd made a developer mandatory. Each over-formalization forced another correction and tired the user. They said plainly: *"I wrote typically, you carved an absolute."*

**How to apply:** Mirror the user's modality. Hedged input → hedged output ("typically a complex, sometimes a single plant — the compiler judges"). For definitions/boundaries on this project, frame them as **working patterns applied with judgment, the decision is the compiler's** — never as a mechanical test. Surface edge cases as "the compiler's call," not as rules to resolve them. See [[feedback-imagine-mode]] (design dialogue = reflect and sharpen, don't over-commit).
