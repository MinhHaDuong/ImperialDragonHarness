Worktree creation was failing (EnterWorktree timed out) because `hooks/post-checkout` did two heavy eager per-worktree operations. Both fixed:

- **uv env** (#797): the uv cache lives on `/data` (`/data/cache/uv`), repos on `/home` — different filesystems, so uv could not hardlink wheels and **copied** the ~1.8 GB torch closure into every `.venv`. Fix: a shared env at `/data/envs/venv/oeconomia` (built once, hardlinked from `/data/cache`), and the hook symlinks each worktree's `.venv` to it (symlinks cross filesystems; hardlinks do not). See the generic rule in [[reference_agent_identity]]'s sibling IDH rule `rules/coding-python.md` (cache + env must share a filesystem).
- **DVC data** (#801): the hook ran `dvc checkout`, copying ~1.7 GB into every worktree (DVC cache is same-fs but default link type copies on ext4). Fix: removed from the hook. Data is now on demand via **`make data`** (`$(UV_RUN) dvc checkout`, local cache, no network); `make corpus-sync` still does the full remote pull. On doudou only, `.dvc/config.local` sets `cache.type = symlink` + `protected = true` so `make data` links instead of copies — NOT on padme (it is the Phase-1 producer that rewrites DVC outs; read-only symlinks would break it).

**Gotcha — `core.hooksPath` is an absolute path** to the main checkout's `hooks/`. So every worktree runs the MAIN checkout's `post-checkout`, not its own. A hook change is live for new worktrees only once the main checkout's working tree is on a commit that has it. A confusing transient: while a parallel session held the main checkout on a pre-fix branch, new worktrees ran the stale (old) hook even though the fix was merged.

**Gotcha — shared-env console scripts carry the building worktree's shebang.** When the shared env is `uv sync`'d from inside a worktree, uv stamps every `bin/` console script (`pytest`, `ruff`, `mypy`, `dvc`, ~52 total) with a shebang pointing at *that worktree's* `.venv/bin/python3` symlink. The worktree is throwaway; once removed the shebang dangles, and `uv run pytest` silently falls through to the **system** pytest (which can't import the venv's plugins → e.g. `pytest: error: unrecognized arguments: -n` from missing xdist). The shared env this memory describes was synced from session `fddacf5c`'s `wt-nohook` worktree, so its scripts pointed there and broke when it was cleaned up (PR #807, 2026-06-18). Discriminator: `uv run python -c "import xdist"` works but `uv run pytest -n` fails → check `head -1 .venv/bin/pytest`. Durable fix, two layers: invoke tools as `$(UV_RUN) python -m <module>` in Makefiles (bypasses the script, PR #807); and for tools with no `-m` entry point (`dvc`), pin the shebangs to the canonical interpreter (ticket 0158, PR #811, 2026-06-18). The Makefile now `export UV_PROJECT_ENVIRONMENT := $(realpath .venv)` so a Make-driven `uv sync` writes the resolved `/data/.../bin/python3` path, not the worktree symlink path; and a `venv-canonicalize` target (idempotent `sed` over `bin/*` shebangs, order-only prereq of `check`/`check-fast`) repairs stale ones uv left behind (uv only rewrites on an actual sync, so a removed worktree's scripts keep dangling). Both machine-agnostic via `realpath` (no-op where `.venv` is a real local dir). Guarded by `tests/test_venv_shebang_canonical.py` (integration). Note: bare interactive `uv run dvc` in a fresh shell still has no `UV_PROJECT_ENVIRONMENT`, so a dep-changing sync there can re-stamp worktree-local until the next `make` run repairs it — run `make venv-canonicalize` if a bare `uv run <tool>` breaks.

Standing regression test for the eager-heavy-setup class: ticket 0157. Rotating pre-existing real `.venv` dirs (e.g. the 2 GB main-checkout one) into symlinks: ticket 0145. Both relate to [[feedback_no_long_running]] (don't pay heavy setup cost per worktree).
