# The `zotero.py` helper

`"$IDH_ROOT/scripts/zotero.py"` (with `IDH_ROOT` resolved from the loaded skill) exposes the subcommands below. It is a PEP 723 uv script (`#!/usr/bin/env -S uv run --script`): run it as `"$IDH_ROOT/scripts/zotero.py" <subcommand>` or `uv run --script "$IDH_ROOT/scripts/zotero.py" ...`; running it with `python3` does not work, and `uv` must be on `PATH`. It is local-only and stateless: each call reads the library live through the running Zotero's local API and keeps nothing between runs but the local API key (see Writes); it never opens `zotero.sqlite`. Every subcommand that reads the library except `report-duplicates` (user library only) takes `--library L` (`user`, the default; `all`; or a numeric groupID, as in `zotero.org/groups/<groupID>`). Every output that comes from a read names its `source` (see the end of this file).

- `extract-metadata <pdf>...` — what each PDF says about itself, as JSON on stdout (`items`): `pdfinfo`, `page_count`, `first_pages_text`, `last_pages_text`, `identifiers` (doi/isbn/handle/arxiv), `year_hint`, `filename`. Input-format dependent (PDF today: poppler's `pdfinfo` and `pdftotext`); it never contacts Zotero or the network, so it runs with Zotero down. Exit 1 when a PDF is missing or unreadable (its row carries `error`).
- `find-work [--metadata FILE|-] [--title T] [--doi D] [--isbn I] [--arxiv A] [--handle H] [--type T] [--pdf P]` — is this work already in the library? Local API only, stateless: it never opens `zotero.sqlite` and never goes to the web. `--metadata` takes `extract-metadata`'s JSON (a file, or `-` for stdin) and looks up each item from its identifiers, pdfinfo title and PDF; a flag overrides the extracted value (the title *you* refined replaces the often-garbage pdfinfo one), and an empty flag (`--doi ""`) is ignored: it does not clear an extracted value; without `--metadata` the flags describe one work, and with it the flags are refused when the file holds several works (they would describe them all as one). An extraction row that carries an `error` comes back as a result with that error (exit 1); `--metadata` that is not extract-metadata output (unreadable, empty, or with `identifiers`/`pdfinfo` that are not objects) is a JSON error, exit 1. It asks Zotero's own search (the local API's `q`, `qmode=everything`) for each key given: DOI, ISBN (in its 10- and 13-digit, bare and hyphenated forms), arXiv id, handle, and the title's words. The only match it asserts is exact: a work whose own field carries the normalised identifier (its DOI or ISBN field, a `DOI:`, `ISBN:` or `arXiv:` line in Extra, its `archiveID` for an arXiv id, or a URL that is itself an arxiv.org or hdl.handle.net link; a DOI mentioned elsewhere in Extra is another work's, and the ISBN a book section, conference paper, encyclopedia article or dictionary entry shares with its volume identifies the volume: such an item never matches on ISBN, and a work of such a type, given with `--type` (or a `.bib` or entry type in check-staging and create-items), is never looked up by it, nor is a `.bib` type check-staging does not map; without `--type` a chapter's ISBN finds its book) (the quick search also returns, say, an item whose abstract quotes the DOI, which is not a match), or a work holding a stored file with the PDF's md5 (`storageHash`, needs the PDF on disk). The title search returns `candidates`, at most 25, for you to judge; a candidate becomes a match only when it holds that very file. Zotero has no search by md5, so a stored copy under a work no key finds goes unseen. A title of fewer than three words of three letters or more is not searched. No lookup reads the whole library. Output: one entry per work in `results`, each with its `query`, `matches` and `candidates` (each carries its item `key`, `why` = which keys found it, `has_file`, `has_pdf`, and `attachment`, the matching attachment record or null), a `verdict` (`match` / `ambiguous` (several matches) / `candidates` / `none` / `unchecked`), and `consulted`/`skipped` so "found nothing" and "could not look" stay distinguishable. Scope defaults to the **user library** (the `create-items` destination); a group-library copy does not count as already present — pass `--library all` or a numeric groupID to widen deliberately. Zotero unavailable → `verdict: "unchecked"`, `zotero: "unavailable"`, exit 75; a read Zotero did not finish in time → `zotero: "slow"`, exit 74.
- `report-duplicates [--out PATH]` — read-only JSON report of identical stored files (same md5) under distinct My Library items, for a reviewed merge in the Zotero client; see `docs/zotero-report-duplicates.md`. It needs Zotero running, like every read, and never edits the library.
- `suggest-edits (--item-key K --expect-title T --set FIELD=VALUE... | --jobs-file J) [--overwrite] [--edit]` — reports the fields to fill on **existing** items; it writes them only with `--edit`. See `references/enrichment.md` for the guards. Output: one row per item with `suggested` (`itemKey`, `field`, `old`, `new`), `refused`, and `status` (`suggested` / `nothing to change` / `not found`; with `--edit`, `written` / `not written`).
- `check-staging [root] [--dir DIR] [--bib PATH]... [--skip-underscore-dirs] [--out PATH] [--apply [--edit]]` — compares staged files with the library, in one of two input modes: by default the files the repository's `.bib` entries link plus the unlinked staging files beside them (`docs/` when there is no `.bib`), or with `--dir` every staging file under that directory of the root. `--bib` (repeatable) and `bib_paths` in `.zotero-reconcile.json` name further `.bib` files of the root, which describe the files they link (under `--dir` too); `--skip-underscore-dirs` leaves out files below `_`-named directories. Only `.pdf .html .htm .jpg .jpeg .png .djvu .epub` are examined. Per file: `verdict` (`identical` / `work_present_with_file` / `work_present_no_file` / `candidates` / `absent` / `unidentified`, the last for a file with no key to look it up by), the matched `zotero_key`/`zotero_title`, `why` (which keys found it), and `consulted`/`skipped`; a `candidates` row lists the works Zotero's search returned for the title (the `.bib` title, else pdfinfo's, else the filename's surnames and slug), for you to judge; when several works match (e.g. one md5 attached to two records), the row also carries `also_matches` naming every other matching parent (ticket 0570). See `references/backfill.md`. Rows the library already holds without a file come back in `suggested_edits`; `--apply --edit` stores those files, `--edit` without `--apply` is an error.
- `suggest-attachments --parent <itemKey> <file>... [--edit]` — checks that the item exists and the files are readable, then reports the attachments to make; with `--edit` it stores a copy of each file under the item. The repair for `work_present_no_file`; also how page-scan images or an HTML snapshot get filed under the work they belong to instead of becoming standalone items.
- `create-items (--entries-json J | --entries-file F) [--collection KEY] [--library L] [--dry-run] [--force]` — creates new items, uploads their PDFs and files them in the collection, all through the local API at `http://127.0.0.1:23119`; see `references/import.md`. `--dry-run` prints the item JSON and creates nothing, but needs Zotero running (field placement uses the live schema). `ZOTERO_CONNECTOR_URL` overrides that address for a client on another port, such as the tests' throwaway Zotero, and is refused unless its host is loopback; `ZOTERO_NO_LAUNCH=1` forbids launching Zotero, for unattended runs that must never start the desktop client (the command then does nothing when Zotero is down); every request ignores proxy settings and refuses redirects. Each entry accepts: `type` (Zotero item type, default `journalArticle`, refused unless the running client's schema lists it; see the classification table in `references/import.md`), `title`, `shortTitle`, `authors` (array; `"First Last"` is auto-converted to `"Last, First"`), `year`, `doi`, `isbn`, `issn`, `url`, `journal` (container title, whatever the type), `volume`, `issue`, `pages` (e.g. `"281-285"`), `numPages`, `publisher`, `place`, `number`, `genre`, `conferenceName`, `edition`, `seriesNumber`, `language`, `abstract`, `pdf`, `attach_pdf` (bool). Any other key is **refused**, not ignored — a misspelt key that silently does nothing is the defect this guard exists to prevent.
  - `number` is the type's identifying number: report number, patent number, standard number.
  - `genre` is the type's kind-of-thing label: `"RAND Paper"` on a report, `"PhD thesis"` on a thesis, `"Working paper"` on a manuscript.
  - `place` is the city of publication (`"Santa Monica, CA"`).

Reads. Every read goes through the local API of Zotero 10 or later (`/api/users/0/...` for the user library, `/api/groups/<groupID>/...` for a group; GET only, no key), so it is live: it sees what the client saved a second ago, and outputs say `source: "zotero local API (live)"`. Trashed items are left out. Attachment files are located from the item JSON (`links.enclosure.href`, a `file://` URL, for stored files; `data.path` for linked files when that path is absolute; a path relative to the linked-attachment base directory is left unresolved, so such a file is not compared). Zotero 10 reports each stored file's md5, which is all the helper compares; an older client is refused (its `X-Zotero-Version` names it). A request Zotero accepts but does not finish within pyzotero's 30 s is a slow read, not an unavailable Zotero: the command says `zotero: "slow"` and exits 74 (`EX_IOERR`), `check-staging` included (verdict `zotero_slow`), since an incomplete read is no clean no-op. The local API is off by default: enable Zotero Settings > Advanced > "Allow other applications on this computer to communicate with Zotero". Disabled, or refusing a request, it makes the command fail (exit 1) with a message naming that setting; a listener on the port that is not Zotero (no `X-Zotero-Version` header) fails the same way, the message saying that something other than Zotero answers at that URL and naming both `ZOTERO_CONNECTOR_URL` and the setting. `ZOTERO_CONNECTOR_URL` (default `http://127.0.0.1:23119`; the name predates the move off the connector and is kept so existing environments still work) points the helper at another Zotero port; a host other than the loopback is refused.

Writes. Writes (`create-items`, and `--edit` on `suggest-edits`, `suggest-attachments`, `check-staging --apply`) go through the same local API. They also need a local API key, stored as `ZOTERO_LOCAL_API_KEY=` in `~/.config/keys/zotero-local.env` (mode 600; `ZOTERO_LOCAL_KEY_FILE` overrides the path), never printed. Without a stored key the helper asks Zotero before the first write, and again on a 401; Zotero shows Allow / Always Allow / Deny, and the helper waits up to 120 s. Tell the user to answer **Always Allow**: it is the only answer the helper accepts, and that key is stored (written through a fresh temporary file, never through a symlink). A one-time "Allow" answer is refused: nothing is written. With no answer or a Deny, nothing is written either, and a batch stops there: the rows after it are reported `not attempted` rather than asked for again. A 401 part-way through storing a file (a stored key Zotero no longer honours) leaves the attachment item without its file; the message names that attachment, and an attachment counts as a stored file only when Zotero reports its md5 or size. No index, cache or ledger is kept.

Zotero not running. The helper launches the desktop client (detached: `zotero` on `PATH`, the usual install directories, or the `org.zotero.Zotero` flatpak) and waits up to 90 s for it to answer; a client it launched that has not answered by then is stopped (only that process, never a Zotero it did not start). It never launches in a container or headless runner (`/.dockerenv`, `/run/.containerenv`, a `container` variable, container names in `/proc/1/cgroup`, `CI`-style variables, or no display on Linux). If Zotero still does not answer, the command does nothing and says so on stderr and in its JSON (`zotero: "unavailable"`; in a `check-staging` report the key holds an object, `{"status": "unavailable", "reason": ...}`), with exit 75 (`EX_TEMPFAIL`, try again later); `check-staging` instead exits 0 with verdict `zotero_unavailable`, so an unattended sweep treats it as a clean no-op; discovery errors (a broken bib, a missing `--dir`) are still listed and make it exit 1; an empty `--dir ""` is refused (exit 1) rather than read as the whole repository. `extract-metadata` never needs Zotero.
