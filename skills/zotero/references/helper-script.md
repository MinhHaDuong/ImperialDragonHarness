# The `zotero.py` helper

`"$IDH_ROOT/scripts/zotero.py"` (with `IDH_ROOT` resolved from the loaded skill) exposes the subcommands below. It is a PEP 723 uv script (`#!/usr/bin/env -S uv run --script`): run it as `"$IDH_ROOT/scripts/zotero.py" <subcommand>` or `uv run --script "$IDH_ROOT/scripts/zotero.py" ...`; running it with `python3` does not work, and `uv` must be on `PATH`. It is local-only and stateless: each call reads the library live through the running Zotero's local API and keeps nothing between runs but the local API key (see Writes); it never opens `zotero.sqlite`. Every subcommand that reads the library except `dedup-report` (user library only) takes `--library L` (`user`, the default; `all`; or a numeric groupID, as in `zotero.org/groups/<groupID>`). Every output that comes from a read names its `source` (see the end of this file).

- `probe <pdf>...` — JSON to stdout. Fields per PDF: `pdfinfo`, `page_count`, `first_pages_text`, `last_pages_text`, `identifiers` (doi/isbn/handle/arxiv), `year_hint`, naive `zotero_matches` (same shape as `match` output, fed from the raw pdfinfo title).
- `match [--title T] [--doi D] [--isbn I] [--arxiv A] [--handle H] [--author FIRST-AUTHOR] [--year Y] [--pdf P]` — deduplication lookup using the metadata *you* refined. Consults its keys strongest first — file content hash (`storageHash`, needs `--pdf` on disk) → persistent identifier (DOI, ISBN, arXiv, handle) → attachment filename → (first author, year, normalised title) → title overlap as last resort — and stops at the first key that fires. Output: `matches` (each hit carries its item `key`, `why` = which key fired, `certainty` = exact/strong/weak, `has_file`, `has_pdf`, and `attachment`, the matching attachment record or null), a `verdict` (`match` / `ambiguous` / `none` / `unchecked`), and `consulted`/`skipped` so "found nothing" and "could not look" stay distinguishable. Scope defaults to the **user library** (the inject destination); a group-library copy does not count as already present — pass `--library all` or a numeric groupID to widen deliberately. A title alone never matches: the author-year-title and title-overlap keys need an author (`--author`), and without one they are listed in `skipped`. Zotero unavailable → `verdict: "unchecked"`, `zotero: "unavailable"`, exit 75.
- `dedup-report [--format html|json] [--out PATH]` — read-only report of identical stored files (same md5) under distinct My Library items, for a reviewed merge in the Zotero client; see `docs/zotero-dedup-report.md`. It needs Zotero running, like every read, and never edits the library.
- `enrich (--item-key K --expect-title T --set FIELD=VALUE... | --jobs-file J) [--overwrite] [--edit]` — reports the fields to fill on **existing** items; it writes them only with `--edit`. See `references/enrichment.md` for the guards. Output: one row per item with `suggested` (`itemKey`, `field`, `old`, `new`), `refused`, and `status` (`suggested` / `nothing to change` / `not found`; with `--edit`, `written` / `not written`).
- `audit <dir> [--out PATH] [--ext ...]` — reconcile a staging directory against the library. Per file: `verdict` (`identical` / `work_present_with_file` / `work_present_no_file` / `ambiguous` / `absent`), the matched `zotero_key`/`zotero_title`, `why` (which key fired), `certainty`, and `consulted`/`skipped`; when several candidates tie at the top certainty tier (e.g. one md5 attached to two records), the row also carries `also_matches` naming every other tied parent (ticket 0570). Summary counts plus the action each verdict calls for on stdout; the full per-file report to `--out`.
- `reconcile [root] [--out PATH] [--apply [--edit]]` — the BibTeX-aware audit of a repository; see `references/backfill.md`. Rows the library already holds without a file come back in `suggested_edits`; `--apply --edit` stores those files, `--edit` without `--apply` is an error.
- `attach --parent <itemKey> <file>... [--edit]` — checks that the item exists and the files are readable, then reports the attachments to make; with `--edit` it stores a copy of each file under the item. The repair for `work_present_no_file`; also how page-scan images or an HTML snapshot get filed under the work they belong to instead of becoming standalone items.
- `inject (--entries-json J | --entries-file F) [--collection KEY] [--library L] [--dry-run] [--force] [--skip-corroboration]` — creates new items, uploads their PDFs and files them in the collection, all through the local API at `http://127.0.0.1:23119`; see `references/import.md`. `--dry-run` prints the item JSON and creates nothing, but needs Zotero running (field placement uses the live schema). `ZOTERO_CONNECTOR_URL` overrides that address for a client on another port, such as the tests' throwaway Zotero, and is refused unless its host is loopback; `ZOTERO_NO_LAUNCH=1` forbids launching Zotero, for unattended runs that must never start the desktop client (the command then does nothing when Zotero is down); every request ignores proxy settings and refuses redirects.
- `write --out <ris-path> --entries-json '<json>'` — writes the combined RIS. Each entry accepts: `type` (RIS code, default `JOUR`), `title`, `shortTitle`, `authors` (array; `"First Last"` is auto-converted to `"Last, First"`), `year`, `doi`, `isbn`, `issn`, `url`, `journal` (container title, whatever the type), `volume`, `issue`, `pages` (e.g. `"281-285"`), `numPages`, `publisher`, `place`, `number`, `genre`, `conferenceName`, `edition`, `seriesNumber`, `language`, `abstract`, `pdf`, `attach_pdf` (bool). Any other key is **refused**, not ignored — a misspelt key that silently does nothing is the defect this guard exists to prevent.
  - `number` is the type's identifying number: report number, patent number, standard number.
  - `genre` is the type's kind-of-thing label: `"RAND Paper"` on a report, `"PhD thesis"` on a thesis, `"Working paper"` on a manuscript.
  - `place` is the city of publication (`"Santa Monica, CA"`).

Reads. Every read goes through the local API of Zotero 7 or later (`/api/users/0/...` for the user library, `/api/groups/<groupID>/...` for a group; GET only, no key), so it is live: it sees what the client saved a second ago, and outputs say `source: "zotero local API (live)"`. Trashed items are left out. Attachment files are located from the item JSON (`links.enclosure.href`, a `file://` URL, for stored files; `data.path` for linked files when that path is absolute; a path relative to the linked-attachment base directory is left unresolved, so such a file is not compared). Zotero 10 reports each stored file's md5; Zotero 7 to 9 do not, and the helper then hashes a stored file only when its size equals the file it compares, in memory, for that run. The local API is off by default: enable Zotero Settings > Advanced > "Allow other applications on this computer to communicate with Zotero". Disabled, or refusing a request, it makes the command fail (exit 1) with a message naming that setting; a listener on the port that is not Zotero (no `X-Zotero-Version` header) fails the same way, the message saying that something other than Zotero answers at that URL and naming both `ZOTERO_CONNECTOR_URL` and the setting. `ZOTERO_CONNECTOR_URL` (default `http://127.0.0.1:23119`; the name predates the move off the connector and is kept so existing environments still work) points the helper at another Zotero port; a host other than the loopback is refused.

Writes. Writes (`inject`, and `--edit` on `enrich`, `attach`, `reconcile --apply`) go through the same local API and need Zotero 10.0 or later; an older client refuses the request and the message names that floor. They also need a local API key, stored as `ZOTERO_LOCAL_API_KEY=` in `~/.config/keys/zotero-local.env` (mode 600; `ZOTERO_LOCAL_KEY_FILE` overrides the path), never printed. On the first write without a key, or on a 401, the helper asks Zotero, which shows Allow / Always Allow / Deny, and waits up to 120 s. Tell the user to answer **Always Allow**: only a remembered key is stored (written through a fresh temporary file, never through a symlink). A one-time "Allow" key covers one keyed write; storing a file takes three (attachment item, upload authorization, upload registration) and a batch one per write, so for those the helper asks before the first write and refuses an "Allow" answer: nothing is written. With no answer or a Deny, nothing is written either, and a batch stops there: the rows after it are reported `not attempted` rather than asked for again. A 401 part-way through storing a file (a stored key Zotero no longer honours) leaves the attachment item without its file; the message names that attachment, and an attachment counts as a stored file only when Zotero reports its md5 or size. No index, cache or ledger is kept.

Zotero not running. The helper launches the desktop client (detached: `zotero` on `PATH`, the usual install directories, or the `org.zotero.Zotero` flatpak) and waits up to 90 s for it to answer; a client it launched that has not answered by then is stopped (only that process, never a Zotero it did not start). It never launches in a container or headless runner (`/.dockerenv`, `/run/.containerenv`, a `container` variable, container names in `/proc/1/cgroup`, `CI`-style variables, or no display on Linux). If Zotero still does not answer, the command does nothing and says so on stderr and in its JSON (`zotero: "unavailable"`; in a `reconcile` report the key holds an object, `{"status": "unavailable", "reason": ...}`), with exit 75 (`EX_TEMPFAIL`, try again later); `reconcile` instead exits 0 with verdict `zotero_unavailable`, so an unattended sweep treats it as a clean no-op; discovery errors (a broken bib) are still listed and make it exit 1. `write` never needs Zotero.
