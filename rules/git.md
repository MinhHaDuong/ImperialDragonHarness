# Git Discipline

- **Always work on a branch.** Main is read-only. Everything (code, docs, tickets, STATE, memory, config) lands via branch + PR. See `rules/workflow.md` § Worktree paths. Sole exception: manuscript prose in paper repos, co-edited in place — see § Prose workpackages below.
- **One change per commit.** Message explains *why this change and not another*: alternatives considered, local design choices made.
- **Merge commits**: strategic-level detail — architecture decisions, cross-file impacts, residual debt. Feature merges go through merge requests; chores merge locally via short-lived branch + fast-forward.
- **Git is the project's long-term memory.** Top-level files reflect *now* — history lives in `git log`.
- **Worktree isolation is automatic** — the SessionStart hook enforces it. All worktrees are throwaway; branches hold durable state. Skills must not manually delete worktrees created via `Agent(isolation:"worktree")` — use `git worktree prune` after branch deletion, never `rm -rf`.
- **Never round-trip through `git stash` in a shared checkout.** The stash stack is repo-global — shared by every worktree and session. On a clean tree `git stash` saves nothing, so the following `pop` grabs *someone else's* stash (this resurrected a deleted ticket file on 2026-06-03, ticket 0193); a conflicted `pop` silently *retains* the entry, re-arming the trap. Need a clean baseline? Use a throwaway `git worktree add` or a WIP commit. If you must stash, use `git stash push -m <name>`, pop only after confirming `git stash list` shows your entry on top, and `git stash drop` it on conflict after resolving.
- **Merge method is per-repo — check before merging.** This harness repo disables squash and uses regular merge commits only (`--merge`), so `git merge-base --is-ancestor` works directly. Other repos may be the opposite: `CIRED/cired.digital` *rejects* merge commits and requires `--squash` (its `gh api repos/...` reports `allow_merge_commit: true`, yet branch protection still bounces `gh pr merge --merge` with "Merge commits are not allowed" — trust the merge attempt, not the API flag). On any squash-merged branch (including ones squash-merged historically before 2026-05-25), `git cherry` shows a `-` prefix but `is-ancestor` is false; confirm the merge via `gh pr view --json state,mergeCommit` before deleting the branch.
- **Create a merge request** for each ticket to review changes before merging. Include one or more `**Ticket:** tickets/NNNN-...` lines in the PR body so `erg-pr-merge` can auto-close the ticket(s) on merge. Use `Ticket-ref: tickets/NNNN-...` to reference a ticket without closing it, or `Ticket: none` for a PR that closes nothing.
- **Rebase at every gate, not just before merge.** Rebase onto current `origin/main` (then push `--force-with-lease` and wait for CI) before each hand-off: opening the merge request, invoking `/gaze`, and merging. Each gate validates the *combination* branch ⊕ base — a verdict on a stale base is partially void, and under parallel sessions staleness accrues continuously (2026-06-04: a PR opened current went 17 commits stale in 18 minutes and burned a full `/gaze` round on the mergeability circuit-breaker). This also prevents "Base branch was modified" failures mid-merge and keeps history linear.
- **Force-push denied → don't rebase a pushed branch; merge as-is.** The rebase-at-every-gate rule assumes `git push --force-with-lease` is available. When a PreToolUse guard denies it, rebasing a branch whose PR is already pushed rewrites its SHAs, so local diverges from `origin/<branch>` and can no longer be pushed. The next `erg-pr-merge` then commits its ticket-close on top of that *local* rewrite and its plain `git push` is rejected non-fast-forward, leaving the ticket closed+archived locally but the close commit unpushed; a re-run fails `close: no ticket found` (2026-07-10, raid 234/235, PR #998). Recovery: `git checkout <origin-branch-tip>` (detached), `git cherry-pick <close-commit>`, fast-forward push, then `gh pr merge --merge` directly. The rebase's only benefit is currency, which `/verify-gate` reports as a non-blocking *nit*. So when force-push is denied: if `mergeStateStatus` is CLEAN and the base is conflict-free (parallel work landed in different files), skip the rebase and let the merge land as-is with a merge commit; only when bases genuinely conflict, integrate with `git merge origin/main` into the branch, never rebase (the idiom the multi-PR-wave bullet already uses), which keeps local == remote after a normal push.
- **After an APPROVED `/gaze`, sync before merging.** `/gaze` may commit and push fixes from its own review worktree, leaving your local branch behind `origin`. Run `git fetch origin && git merge --ff-only origin/<branch>` before you rebase/merge — otherwise a rebase + `--force-with-lease` silently drops the verify fix.
- **Multi-PR wave on one file: fetch before each sibling merge, then grep-verify the union.** When several PRs of a wave touch the same file, integrate them one at a time and `git fetch origin` *immediately* before each `git merge origin/main` into the next branch. A stale `origin/main` ref — e.g. you merged sibling N with `gh pr merge` but did not fetch before merging into N+1 — produces a clean-looking auto-merge that silently drops N's non-conflicting additions: no conflict reported, exit 0, wrong content (2026-07-08: a three-PR manuscript wave lost two siblings' citations this way, caught only by grepping the merged file for each new `@key`). "Auto-merging `<file>`" + a clean exit is not proof the union survived — after resolving, grep the result for every sibling's markers before committing. On a drop, don't hand-patch: `git checkout origin/main -- <file>` (known-good, carries the merged siblings) and re-layer only *this* PR's small change on top, then re-verify. This is the merge-side analogue of the rebase drop-cascade; force-push being denied, integrate with `git merge origin/main` into the branch, not rebase.
- **Anchor branch-mutating git across a forked-skill boundary.** After a `context:fork` sub-skill or an `isolation:"worktree"` Agent returns, the shell cwd may have been reset into a different worktree than the conversation assumes (2026-06-06: a `/gaze` fork returned with cwd on a foreign checkout; an unanchored `git switch` + `merge --ff-only` compound ran against the wrong tree and only surfaced when a later Read showed pre-rewrite content). Before the FIRST branch-mutating git (`switch`/`checkout`/`merge`/`rebase`/`commit`/`push`/`reset`) in that turn, either confirm the tree with `git rev-parse --show-toplevel` or anchor explicitly with `git -C <worktree-path> …` (or `cd <path> && …` in the *same* compound — a `cd` in a previous call does not persist). Post-fork rule only: in linear flow the worktree shell self-resets after every command and plain git is correct (the `cd <primary> && <mutate>` variant is already blocked by a guard — see `rules/workflow.md` § Worktree paths for the `git -C` idiom, and `scripts/guard-cd-primary-repo.sh`).
- **Merge-bounce recovery.** `erg-pr-merge` legitimately bounces in sequence; each bounce has a specific retry — do not blanket-fall back to `gh pr merge`:
  - *"close: no ticket found" on a retry* — the FIRST run already `erg close`d + archived + pushed the close commit (the script is **not** idempotent past that step). Do NOT re-run it and do NOT hand-close the ticket; the close commit is already on the branch, so finish with `gh pr merge <N> --merge` directly once CI is green.
  - *"must run from PR branch" after a fast-forward* — HEAD detached after `merge --ff-only`; `git checkout <branch>`, then retry.
- **Delete branches after merge.** `deleteBranchOnMerge` is per-repo — check it, don't assume. Where it is `true` (e.g. the harness repo) the remote branch disappears automatically when a PR merges; where it is `false` (e.g. `CIRED/cired.digital`, confirmed 2026-06-23 — and `gh pr merge --delete-branch` does *not* override it, plus its client-side checkout step can abort from a worktree, leaving the remote branch alive) you must delete the remote branch manually: `git push origin --delete <branch>`. Verify with `gh api repos/<owner>/<repo> --jq .delete_branch_on_merge`. Either way, clean up stale local branches with:
  ```bash
  git fetch --prune
  cur=$(git branch --show-current)
  for b in $(git for-each-ref --format='%(refname:short)' refs/heads/); do
    [ "$b" = main ] && continue     # main is always an ancestor; nothing protects it when HEAD is detached
    [ "$b" = "$cur" ] && continue   # never delete the branch you are standing on
    git merge-base --is-ancestor "$b" origin/main && git branch -D "$b"
  done
  ```
  The old `git branch -vv | awk '/: gone]/'` pipeline silently no-ops under rtk output rewriting; the merge-probe loop keys on exit code, not parsed stdout, so it stays robust under any hook. The `main` and current-branch guards are load-bearing: with the primary checkout detached, `git branch -d main` succeeds (2026-06-10: the unguarded loop deleted local main during a /roar hygiene pass; recovered via `git branch --track main origin/main`). The loop uses `-D` deliberately: `-d` checks merged-into-HEAD, not merged-into-origin/main, so it spuriously refuses — and silently leaves behind — merged branches whose upstream is gone (deleteBranchOnMerge) or when HEAD is a stale detached commit; the `merge-base --is-ancestor` probe has just proven the branch is contained in origin/main, which is exactly the safety `-d` is meant to provide. The healthcheck's branch hygiene check flags stale locals; this is how to resolve them. Outside this probe-guarded loop, do not use `git branch -D` on a branch whose PR you have not verified is merged.
- **Propose `/roar` after a merge lands.** When a merge request merges, offer the post-task wrap-up (`/roar`) rather than stopping silently — it reflects on the work, saves durable lessons to memory, refreshes project state, and cleans up branches. Propose, don't auto-run: the author decides whether to wrap up or push on to the next task.
- **Don't gitignore handoff artifacts.** Generated files that a downstream workpackage consumes (figures, tables, macros `\input`ed by the manuscript) are durable state — commit them. Caches, LaTeX aux files, and the final rendered PDF are regenerable — gitignore.
- **Prose workpackages are edited in place, not behind a worktree.** In paper repos, worktree + branch + PR discipline applies to code and data workpackages (`analysis/`, scripts, pipelines) — agent-produced, test-verifiable, reviewed as a diff. Manuscript prose is co-edited with the author in short interactive turns; isolation cuts him off from the text (decided 2026-07-06, after the Œconomia annotated-ODT round-trips). In interactive sessions, edit manuscripts directly in the author's checkout and commit at session end or milestones, on main or on a paper branch checked out there — no throwaway worktree. The review interface for prose is the recompiled PDF and `latexdiff` between tags, not a PR diff. Autonomous passes on prose produce *reports* (referee panels, source registers, biblio saturation → `conception/` notes), never direct manuscript edits; an autonomous change to a manuscript goes through branch + PR for the author to arbitrate — and the two modes never run concurrently on the same file. Collision protection comes from lane separation (autonomous tickets touch `analysis/`, `conception/`, `refs.bib`), not git isolation. Scope: paper repos only — the harness repo keeps its no-exceptions PR gate.
- **Name workpackage directories in plain language.** In multi-paper repos, directories are named by content (`marches-carbone/`, `arbitrage-onchain/`), never by opaque program codes (`p1/`, `p3/`, `het/`). Program codes stay in tickets and conception notes as cross-references (decided 2026-07-06).
